10 Rules of AI-Augmented Engineering

How we build with AI on this team. Read it once, then hold each other to it in review.

  1. 1
    Always

    You merge it, you own it.

    If it's in your PR, it's your code. Saying the AI wrote it won't get you out of a review comment, and it helps even less on an incident call.

    In practiceYou should be able to explain any line in the diff without scrolling back through the chat.

  2. 2
    Plan

    Write the spec before the prompt.

    Before you generate anything, write down what it should do, what it shouldn't touch and how you'll know it works. Vague prompts get you code that looks right and isn't.

    In practiceIt doesn't need to be long. A few lines in the ticket or PR description will do, and they double as your test cases.

  3. 3
    Plan

    A person defines the interfaces.

    Types, schemas and API contracts are written by someone on the team. The AI can implement against them, but it doesn't get to change them. Any PR that touches a contract gets a proper look.

    In practiceWrite and commit the types first, then let the AI build against them.

  4. 4
    Build

    One feature per PR.

    Each PR does one thing. If a reviewer can't get through the diff in one sitting, split it.

    In practiceCommit before you run the agent so a bad run is easy to throw away. If a merged PR turns out to be wrong, you revert that one PR without pulling other features out with it.

  5. 5
    Build

    Expect to iterate.

    The first output is rarely the one you keep. Run it, read it, adjust the prompt and run it again.

    In practiceIf the output is wrong, fix the spec or prompt and regenerate. Hand-patching a bad generation hides why it went wrong, and the next run will make the same mistake.

  6. 6
    Verify

    Read every line you ship.

    Writing code is cheap now. Reading it properly still takes time, and that's where yours should go. If you can't explain a change without asking the AI again, don't merge it.

    In practiceDo a task by hand at least once before you hand it off. Otherwise you won't notice when the AI gets it subtly wrong.

  7. 7
    Verify

    No green tests, no merge.

    AI-written code goes through the same CI, security scans and review as everything else. Looking fine isn't a reason to skip any of them.

    In practiceThe AI can write tests too, but check them. A test that can't fail tells you something is covered when it isn't.

  8. 8
    Verify

    Slow down on auth, security and data.

    Changes in these areas get a slow, line-by-line review, even when the diff is small.

    In practiceDon't paste secrets, credentials or client data into a prompt. Before using a tool on client work, find out where it sends and keeps what you type.

  9. 9
    Sustain

    Make code easy to delete.

    Keep modules small and behind clear interfaces. Generated code is cheap to rewrite, so you want throwing it away to be cheap as well.

    In practiceIf you can't say what a module does in one sentence, split it.

  10. 10
    Sustain

    Treat prompts like code.

    Prompts, agent instruction files and shared context live in the repo and get reviewed like anything else. A consistent codebase helps too, since agents copy whatever patterns they find.

    In practiceUpdate them in the same PR as the code they affect.

These only work if something checks them. Each rule should map to a PR template checkbox, a CI step or something reviewers look for.
